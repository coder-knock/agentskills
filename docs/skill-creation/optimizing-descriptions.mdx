只有被激活的技能才有用。`SKILL.md` frontmatter 中的 `description` 字段是智能体决定是否为给定任务加载技能的主要机制。描述不足意味着该触发时不会触发；描述过宽则会在不该触发时触发。

本指南介绍如何系统地测试和改进技能描述，以提高触发准确率。

## 技能触发的工作原理

智能体使用[渐进式披露](/specification#progressive-disclosure)来管理上下文。在启动时，它们只加载每个可用技能的 `name` 和 `description`——仅足以判断某个技能是否可能相关。当用户的任务与某个描述匹配时，智能体才会将完整的 `SKILL.md` 读入上下文并遵循其指令。

这意味着描述承担了触发的全部责任。如果描述没有传达出技能何时有用，智能体就不会知道应该使用它。

一个重要的细微差别：智能体通常只在需要超出其自身能力的知识或能力时才咨询技能。像"读取这个 PDF"这样的简单、单步请求可能不会触发 PDF 技能，即使描述完全匹配，因为智能体可以用基本工具处理它。涉及专业化知识的任务——不熟悉的 API、特定领域的工作流或不常见的格式——才是编写良好的描述能够发挥作用的地方。

## 编写有效的描述

在测试之前，了解好的描述长什么样会有帮助。几个原则：

- **使用祈使句式措辞。** 将描述作为对智能体的指令来表述："当……时使用此技能"，而不是"此技能用于……"。智能体正在决定是否行动，所以告诉它何时行动。
- **关注用户意图，而非实现方式。** 描述用户试图实现什么，而非技能的内部机制。智能体根据用户请求的内容进行匹配。
- **宁可偏于主动。** 明确列出技能适用的上下文，包括用户未直接提及领域名称的情况。
- **保持简洁。** 几句话到一段短文通常就足够了——足够覆盖关键用例但不会使智能体的上下文膨胀。[规范](/specification#description-field) 对所有技能的总描述字符数强制执行 1024 个字符的硬性限制。

## 设计触发评估查询

要测试触发效果，你需要一组评估查询（eval queries）——标记了是否应触发技能的真实用户提示词。

```json eval_queries.json
[
  { "query": "I've got a spreadsheet in ~/data/q4_results.xlsx with revenue in col C and expenses in col D. Can you summarize the net profit by month?", "should_trigger": true },
  { "query": "whats the quickest way to convert this json file to yaml", "should_trigger": false }
]
```

目标大约 20 条查询：8-10 条应触发和 8-10 条不应触发的。

### 应触发的查询

这些查询测试描述是否准确捕获了技能的范围。沿多个维度变化：

- **措辞**：有些正式、有些随意、有些有拼写错误或缩写。
- **明确程度**：有些直接点名技能领域（"分析这个 CSV"），有些则描述任务而不命名领域（"我需要从这个电子表格中提取数字"）。
- **细节**：混合简洁提示词和包含大量上下文的提示词——简短的"分析我的销售 CSV 并制作图表"和详细的提示词都应触发。
- **复杂度**：变化的步骤数量和决策点。包括单步任务和多步骤工作流。

最有价值的应触发查询是那些技能有帮助但连接并不明显的查询——如果用户明确说了"使用 X 技能"，那就不需要好的描述。

### 不应触发的查询

这些查询测试描述是否避免误触发。同样沿多个维度变化：

- **相邻领域**：听起来相似但不属于技能范围的任务（例如，对于 CSV 分析技能来说，"将 JSON 转换为 CSV"）。
- **通用工具使用**：可以通过通用工具完成的任务（例如，"读取这个文件"、"运行 npm install"）。
- **错误匹配**：碰巧包含关键词但实际无关的任务（例如，对于数据分析技能来说，"分析为什么我的构建失败了"）。

## 运行评估

一旦你有了评估查询集，就可以对每条查询运行评估以检查技能是否正确触发。

## 基于结果迭代

评估通常会揭示模式：

### 如果不应触发的查询触发了技能

描述可能过于宽泛。尝试：
- 添加更多具体约束条件
- 移除过于通用的关键词
- 缩小适用范围

### 如果应触发的查询未触发技能

描述可能过于狭窄或缺少关键词。尝试：
- 添加用户可能使用的同义词或替代措辞
- 扩展涵盖的相关用例
- 使触发信号更加明确

### 阈值调优

触发是一个概率问题——不存在完美的阈值能在零误报的情况下捕获所有合法用例。目标是找到适合你技能的平衡点。对于低风险技能（如掷骰子），偏于主动更好。对于高风险技能（如修改生产数据库），偏于保守更安全。
