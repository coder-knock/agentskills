## 从真实专业知识出发

技能创建中的一个常见陷阱是要求 LLM 在没有提供领域特定上下文的情况下生成技能——完全依赖 LLM 的通用训练知识。结果是模糊、通用的流程（"适当处理错误"、"遵循认证最佳实践"），而不是使技能有价值的特定 API 模式、边界情况和项目约定。

有效的技能建立在真实的专业知识之上。关键是在创建过程中注入领域特定的上下文。

### 从实际操作任务中提取

与智能体对话完成一个真实的任务，在此过程中提供上下文、纠正和偏好设置。然后将可复用模式提取到技能中。重点关注：

- **有效的步骤** — 导致成功的操作序列
- **你做出的纠正** — 你引导智能体方向的地方（例如，"使用库 X 而不是 Y"、"检查边界情况 Z"）
- **输入/输出格式** — 数据进入和输出的样子
- **你提供的上下文** — 智能体不知道的项目特定事实、约定或约束

### 从现有项目产物综合

当你拥有大量现有知识时，可以将其提供给 LLM 并要求其综合成技能。从团队实际的事件报告和运行手册中综合出的数据管道技能，将优于从通用的"数据工程最佳实践"文章中生成的技能，因为它捕获了*你的*模式、故障模式和恢复流程。关键是项目特定材料，而非通用参考。

好的源材料包括：

- 内部文档、运行手册和风格指南
- API 规范、schema 和配置文件
- 代码审查评论和问题追踪（捕获反复出现的关注点和审查者期望）
- 版本控制历史记录，尤其是补丁和修复（通过实际发生的事情揭示模式）
- 真实世界的失败案例及其解决方案

## 通过实际执行来优化

技能的初稿通常需要优化。将技能应用于实际任务，然后将执行反馈回技能中。即使单次执行-修订循环也能明显提升质量，复杂领域通常需要多轮迭代。

<Tip>
阅读智能体执行轨迹，而不仅仅是最终输出。如果智能体在无生产力的步骤上浪费时间或遗漏了关键细节，这些是技能需要改进的信号。
</Tip>

关于包含测试用例、断言和评分的更结构化迭代方法，请参阅[评估技能](/skill-creation/evaluating-skills)。

## 合理使用上下文

一旦技能激活，其完整的 `SKILL.md` 正文就会连同用户消息一起加载到智能体的上下文窗口中。每个字符都会消耗可用空间——因此要明智地使用它。

<Warning>
避免使用长篇示例、冗长的教程或大段复制粘贴的文档作为技能正文内容。这会快速耗尽上下文窗口，导致智能体截断或忽略重要指令。
</Warning>

相反，应引用外部资源并将详细说明放在脚本中：

- **引用外部文档** — 链接到 API 文档、规范或运行手册，而不是嵌入它们
- **将详细步骤放入脚本** — 将复杂的命令序列移至 `scripts/` 中的 shell 或 Python 脚本；在正文中仅保留高层指导
- **保持示例简短且有针对性** — 使用最小代码片段来说明特定模式，而非完整教程

## 编写精准的描述

`description` 字段是智能体决定是否激活技能的主要信号。模糊的描述会导致误触发（在不合适时激活）或漏触发（在需要时未激活）。

### 做什么

- **具体说明适用场景** — "用于从 PostgreSQL 数据库导出数据到 CSV 格式"
- **提及关键约束** — "仅支持只读查询；不执行写入或修改操作"
- **定义清晰的范围** — "处理 JSON 和 YAML 配置文件；不支持 XML"

### 避免什么

- **模糊的声明** — "数据处理工具"、"帮助管理文件"
- **夸大的范围** — 不要声称技能能做超出其可靠能力范围的事情
- **通用模板** — "一个用于 [X] 的技能"，其中 [X] 过于宽泛

## 测试跨平台兼容性

技能可能在一种环境中工作但在另一种环境中失败。在不同配置中测试技能以识别依赖关系和假设。

<Note>
脚本尤其容易出现兼容性问题。始终在目标环境中测试脚本，并考虑提供多个实现（例如 bash + PowerShell）。
</Note>

常见问题包括：

- **Shell 假设** — 脚本假设 `bash` 但目标系统使用 `sh` 或缺少 POSIX 扩展
- **工具依赖** — 脚本依赖 `jq`、`yq` 或其他可能未安装的工具
- **路径假设** — 硬编码路径或对目录结构的假设在不同操作系统上失效
- **权限问题** — 脚本在没有必要权限的环境中运行
