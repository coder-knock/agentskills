你写了一个技能，在一个提示词上试了一下，看起来能用。但它是否可靠地工作——在各种提示词、边界情况下，比没有技能时更好吗？运行结构化评估（evals）可以回答这些问题，并为你提供系统改进技能的反馈循环。

## 设计测试用例

一个测试用例包含三个部分：

- **提示词（Prompt）**：一条真实的用户消息——人们实际会输入的那种。
- **预期输出（Expected output）**：对成功样貌的人类可读描述。
- **输入文件（Input files）**（可选）：技能需要处理的文件。

将测试用例存储在技能目录内的 `evals/evals.json` 中：

```json evals/evals.json
{
  "skill_name": "csv-analyzer",
  "evals": [
    {
      "id": 1,
      "prompt": "I have a CSV of monthly sales data in data/sales_2025.csv. Can you find the top 3 months by revenue and make a bar chart?",
      "expected_output": "A bar chart image showing the top 3 months by revenue, with labeled axes and values.",
      "files": ["evals/files/sales_2025.csv"]
    },
    {
      "id": 2,
      "prompt": "there's a csv in my downloads called customers.csv, some rows have missing emails – can you clean it up and tell me how many were missing?",
      "expected_output": "A cleaned CSV with missing emails handled, plus a count of how many were missing.",
      "files": ["evals/files/customers.csv"]
    }
  ]
}
```

**编写好的测试提示词的技巧：**

- **从 2-3 个测试用例开始。** 在看到第一轮结果之前不要过度投入。早期迭代通常能揭示最大的问题，而无需完整套件。
- **变化提示词措辞。** 使用不同的表达方式、详细程度和正式程度。有些提示词应该简洁直接（"分析这个 CSV"），有些则应模糊或非正式（"看看这个电子表格"）。真实用户不会使用一致的术语。
- **覆盖边界情况。** 至少包含一个测试边界条件的提示词——格式错误的输入、空文件、异常大的文件等。
- **使用真实的上下文。** 真实用户会提到文件路径、列名和个人上下文。提示词应反映这一点："我的 `data/q4_results.xlsx` 文件中 C 列是收入，D 列是支出"。避免像"这是一个 CSV 文件"这样通用且不切实际的提示词。

暂时不用担心定义具体的通过/失败检查——只需写好提示词和预期输出即可。下一节介绍如何运行它们并判断结果。

## 运行评估

核心模式是对每个测试用例运行两次：一次**启用技能**，一次**不启用技能**。比较两者可以揭示技能是否真正增加了价值，以及智能体在无技能时是否会自然地完成任务。

### 工作区结构

在工作区目录中组织评估结果，与技能目录并列。每次迭代都会创建一个新的带时间戳文件夹：

```
csv-analyzer/
├── SKILL.md
└── evals/
    └── evals.json
csv-analyzer-workspace/
└── iteration-1/
    ├── eval-top-months-chart/
    │   ├── with_skill/
    │   │   ├── outputs/       # 运行生成的文件
    │   │   ├── timing.json    # Token 数和耗时
    │   │   └── trace.md       # 智能体的逐步执行记录
    │   └── without_skill/
    │       ├── outputs/
    │       ├── timing.json
    │       └── trace.md
    └── eval-clean-customers/
        ├── with_skill/
        │   ├── outputs/
        │   ├── timing.json
        │   └── trace.md
        └── without_skill/
            ├── outputs/
            ├── timing.json
            └── trace.md
```

### 执行单次评估运行

<Tabs sync={false}>
  <Tab title="Claude Code">
    ```bash
    claude --skill csv-analyzer -p "<prompt>" > with_skill/trace.md 2>&1
    claude -p "<prompt>" > without_skill/trace.md 2>&1
    ```
  </Tab>
  <Tab title="GitHub Copilot">
    在 VS Code 中打开 Copilot Chat 面板：
    
    1. 选择 **Agent** 模式以启用技能发现
    2. 输入提示词并保存输出到 `with_skill/trace.md`
    3. 禁用技能（从 `.agents/skills/` 中移除或重命名技能文件夹）
    4. 用相同的提示词再次运行并保存到 `without_skill/trace.md`
  </Tab>
</Tabs>

### 记录元数据

每次运行后，创建一个 `timing.json` 文件来捕获定量指标：

```json timing.json
{
  "run_id": "iteration-1-eval-1-with-skill",
  "timestamp": "2026-01-15T10:30:00Z",
  "model": "claude-opus-4-6",
  "duration_seconds": 12.5,
  "input_tokens": 245,
  "output_tokens": 1820,
  "total_tokens": 2065,
  "skill_name": "csv-analyzer",
  "eval_id": 1
}
```

## 分析结果

对每对运行（有技能 vs 无技能），检查三个维度：

### 1. 输出质量

将实际输出与 `expected_output` 描述进行比较。问自己：

- 输出是否符合预期的格式和结构？
- 结果在事实层面正确吗？（正确的数字、正确的图表类型等）
- 是否有遗漏或多余的输出？
- 有技能的版本是否明显优于无技能的版本？

### 2. 效率

比较 `timing.json` 指标：

- 哪次运行更快？（考虑总耗时）
- Token 使用量如何？技能是否显著增加或减少了 token 消耗？
- 智能体是否走了弯路还是遵循了直接路径？

### 3. 可靠性模式

跨多个测试用例寻找模式：

| 模式 | 含义 | 行动 |
|------|------|------|
| 技能在所有用例上均优于无技能 | 技能提供了明确的价值 | 准备发布 |
| 技能在某些用例上更好，某些更差 | 部分范围有效 | 缩小描述范围或改进弱点的指令 |
| 无技能与技能表现相当 | 智能体已经知道如何做此任务 | 考虑扩展技能以覆盖更专业的场景 |
| 技能更差 | 技能指令具有误导性或过于严格 | 重写正文内容 |

## 迭代改进

评估是一个循环，而非一次性事件。根据结果更新技能，然后重新运行。

### 更新什么

基于失败模式，你可能需要更改不同的部分：

<Accordion title="当触发失败时（技能未激活）">
更新 `description` 字段。添加用户使用的同义词，使适用场景更明确，或移除令人困惑的关键词。参见[优化技能描述](/skill-creation/optimizing-descriptions)获取详细指南。
</Accordion>

<Accordion title="当输出错误时（技能激活但产生不良结果）">
更新 `SKILL.md` 正文内容。澄清指令，添加缺失的步骤，修正错误的命令，或加强约束条件。确保示例准确反映了期望的行为。
</Accordion>

<Accordion title="当输出不一致时（有时成功有时失败）">
同时检查 `description` 和正文内容。不一致通常意味着描述在某些上下文中过度承诺，或者正文缺少处理边缘情况的指导。
</Accordion>

### 何时停止迭代

当满足以下条件时，技能已准备好发布：

- 所有测试用例在有技能时均产生正确或可接受的输出
- 有技能的表现一致地等于或优于无技能
- 连续两轮迭代之间没有回归
- 你已测试至少 8-10 条多样化的提示词

<Tip>
完美不是目标。如果技能在 80% 的相关查询上可靠地工作并且不造成损害，它就比没有技能要好。剩余的 20% 可以在后续版本中解决。
</Tip>
